# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PDV Agência Sigma — a multi-tenant restaurant ordering platform. One agency (ADM) manages many restaurant tenants, each with their own menu, tables, and orders; end customers order through a public storefront. All user-facing text, SQL comments, and code comments are in Portuguese (pt-BR) — keep new UI copy and comments in Portuguese to match. `PDV.md` (pt-BR) is a narrative, screen-by-screen product walkthrough for humans, kept in sync with the current model (`/loja/:restaurantId`, real customer accounts with a profile screen, addons/combos/half-and-half, the printing agent, etc.) — treat it as accurate, not historical; update it alongside this file when a screen or flow changes. This file (`CLAUDE.md`) stays terser and code-anchored; `PDV.md` explains the same system in prose for a non-technical reader.

## Repository layout

This is **three independent Vite apps and one Go binary, sharing one Supabase backend**, not a single app:

- `/` (root, package `pdv-agencia-sigma`) — the customer-facing storefront. Talks to Supabase directly (`@supabase/supabase-js`) via `src/lib/supabase.ts`; menu data is loaded live by `src/lib/useMenu.ts` — there is no static/mock menu.
- `admin/` — the agency's internal dashboard: restaurant CRUD, onboarding Kanban, cross-tenant order view, account status, audit log. Requires an `admin` role profile.
- `restaurante/` — the restaurant owner/staff app: invite-based signup (`Cadastro`), login, dashboard, cardápio (menu) management, live order management (`Pedidos`), and printer setup (`Impressora`). Requires a `restaurant_owner`/`restaurant_staff` profile.
- `supabase/` — the shared backend: SQL migrations (`supabase/migrations/`) and Deno Edge Functions (`supabase/functions/`).
- `agente/` — the local ticket-printing agent (Go, not a Vite app): a single binary that runs on a computer in the restaurant and talks to `restaurante/` over `http://127.0.0.1:18080`. See "Ticket printing" below and `agente/README.md`.

Each of `admin/` and `restaurante/` is a fully separate npm project (own `package.json`, `node_modules`, `.env.local`) — always `cd` into the specific app directory before running its scripts. `agente/` is a separate Go module (own `go.mod`) — see its own build commands below, not `npm`. The Supabase project ref is `qedslrbzgklsxcbuokbl` (see `.mcp.json`); the Supabase MCP server is enabled for this repo, so prefer its tools (`list_tables`, `execute_sql`, `apply_migration`, `get_advisors`, `query_logs`, `deploy_edge_function`, etc.) over raw `supabase` CLI calls when inspecting or changing the live backend.

## Commands

Run from inside the relevant app directory (root, `admin/`, or `restaurante/`) unless noted:

```
npm run dev       # vite dev server — root:5173 (default), admin:5174, restaurante:5175
npm run build     # tsc -b && vite build
npm run lint      # oxlint (each app has its own .oxlintrc.json)
npm run preview   # vite preview
```

Tests exist **only in `admin/`** (vitest, `admin/src/lib/*.test.ts`):

```
cd admin && npm test                              # vitest run
cd admin && npx vitest run src/lib/orders.test.ts # single file
cd admin && npx vitest run -t "order_type"        # single test by name
```

These are pure-function tests with no DB or React involved — the most useful pattern in them is asserting that UI label maps cover every enum value declared in `supabase/migrations/0001_init.sql`, so a new DB enum value that the UI forgot to map fails the build instead of rendering blank. Extend that pattern when adding enum-backed UI.

`agente/` is a separate Go module — run its commands from inside `agente/`, not with `npm`:

```
go test ./...                                                                    # unit tests (escpos renderer + HTTP API), run on any OS
go vet ./...                                                                     # also run once with GOOS=windows to catch Windows-only build issues
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags "-s -w -H=windowsgui" -o dist/ImpressoraPDVSigma.exe ./cmd/agente
```

The build cross-compiles fine from Linux/WSL — no Windows machine needed to produce the `.exe`. Publishing a new build requires a manual copy into `restaurante/public/downloads/ImpressoraPDVSigma.exe` (see "Ticket printing" below); there is no CI step that does this automatically.

Edge functions live under `supabase/functions/<name>/index.ts` (Deno). Deploy with the Supabase MCP tool `mcp__supabase__deploy_edge_function`, not a local build step. Migrations are plain numbered SQL files in `supabase/migrations/`; apply with `mcp__supabase__apply_migration`. The numbering has a gap (0027–0029 never existed) — keep appending after the highest number rather than filling it.

## Domínios e DNS (produção)

`assessoriasigma.com.br` (registrado na Hostinger) tem as nameservers **totalmente delegadas pra Vercel** (`ns1`/`ns2.vercel-dns.com`) — isso é obrigatório pro certificado wildcard (`*.assessoriasigma.com.br`) funcionar, não dá pra fazer só com CNAME/A apontado da Hostinger (ver seção "Ordering flow" mais abaixo sobre subdomínio por restaurante). A zona DNS de verdade agora é a da própria Vercel — mudar algo na Hostinger não tem efeito nenhum, ela só guarda o registro do domínio.

Mapeamento domínio → projeto Vercel (`vercel domains inspect assessoriasigma.com.br` mostra isso ao vivo):
- `assessoriasigma.com.br` (apex, sem subdomínio) **e** `*.assessoriasigma.com.br` (wildcard, cada restaurante) → projeto `sigma-pdv-loja` (storefront raiz).
- `adm.assessoriasigma.com.br` → `sigma-pdv-admin`.
- `app.assessoriasigma.com.br` → `sigma-pdv-restaurante`.

**Regra permanente: nunca adicionar registro A/CNAME/ALIAS manual pra `@` (apex) ou `*` (wildcard) na zona DNS da Vercel.** Com a nameserver 100% na Vercel, ela já gerencia isso sozinha via um ALIAS automático (aparece como `default` em `vercel dns ls assessoriasigma.com.br`) assim que o domínio está atribuído a um projeto — e também renova o certificado sozinha. Um registro manual nesses nomes só compete com esse ALIAS automático e quebra a resolução (ver incidente abaixo). Se precisar de um novo domínio/subdomínio de produção, o único passo é `vercel domains add <domínio> <projeto>` — nunca mexer em registros DNS crus pra isso.

**Incidente (2026-08-20)**: o domínio raiz ficava caindo aleatoriamente numa página de "domain parking" da Hostinger em vez do app, e o wildcard chegou a dar 403. Duas causas, ambas resolvidas:
1. Sobrou um registro A manual em `@` apontando pro IP de parking da Hostinger — resquício de uma tentativa antiga de configurar o wildcard antes da migração de nameserver ter sido concluída, nunca removido depois. Ele competia com o ALIAS automático da Vercel, e a resolução de DNS alternava entre os dois aleatoriamente. Corrigido removendo os 2 registros A manuais de `@` (`vercel dns rm`).
2. O domínio "nu" (`assessoriasigma.com.br` sem subdomínio) nunca tinha sido de fato atribuído a nenhum projeto Vercel — só o wildcard estava. Sem essa atribuição, o certificado SSL emitido só cobria `*.assessoriasigma.com.br` (SAN de wildcard não cobre a apex sozinha), então HTTPS na apex quebrava com erro de certificado. Corrigido com `vercel domains add assessoriasigma.com.br sigma-pdv-loja`.

Se o site cair de novo pra uma página estranha ou erro de certificado: primeiro rodar `vercel domains inspect assessoriasigma.com.br` (confere se a apex e o wildcard estão nos projetos certos) e `vercel dns ls assessoriasigma.com.br` (confere se não tem registro manual novo em `@`/`*` além dos `default` da própria Vercel) — não sair recriando registros DNS por tentativa e erro.

## Backend architecture (Supabase)

**Tenancy model**: `restaurants` (tenant) → `profiles` (role: `admin` | `restaurant_owner` | `restaurant_staff` | `customer`, each linked to at most one `restaurant_id`) → `categories`/`products`/`tables`/`orders` scoped by `restaurant_id`. A Postgres trigger (`handle_new_user`) auto-creates a `customer` profile for every new `auth.users` row; staff/admin roles are never self-assigned — only elevated via the invite flow or an admin Edge Function.

**RLS is the primary authorization layer.** Two `security definer` helper functions, `current_app_role()` and `current_restaurant_id()`, read the caller's own profile and are used throughout the policies to avoid recursive RLS lookups. `categories`/`products`/`tables` are publicly readable (anon + authenticated) since the storefront needs to render menus without login; writes are restricted to the tenant's own staff/admin. When adding tables or columns, follow this same pattern (helper-function based policies, not inline subqueries) and re-run `get_advisors` after schema changes.

**Migration history is instructive** — several early migrations (`0002`–`0005`) are sequential fixes to the same RLS/trigger bugs (PUBLIC vs. named-role grants, and `security definer` swallowing `current_user` so Edge Functions running as `service_role` got blocked by `prevent_role_escalation`). Read `0004` and `0005` before touching that trigger again — the fix requires the trigger function to *not* be `security definer` so `current_user` reflects the real caller.

**Invite flow** (`0006_instant_invite_link.sql` + `check-invite`/`complete-invite` functions): creating a restaurant issues a random `invite_token` immediately, no owner form up front. `check-invite` (public) validates a token without leaking restaurant data. `complete-invite` (public) lets the owner pick their own email/password; `handle_new_user` reads `invite_token` from `raw_user_meta_data` and links the profile to the pending restaurant in the same insert — this path is a single INSERT, so it bypasses the UPDATE-only `prevent_role_escalation` trigger entirely.

**Admin Edge Functions** (`admin-create-restaurant`, `admin-manage-owner`, `admin-reset-password`, `admin-set-account-status`) all gate through `supabase/functions/_shared/admin-guard.ts`'s `requireAdmin()`: it validates the caller's JWT with an anon client, then checks their `profiles.role === 'admin'` via a service-role client before returning that service-role client for the privileged operation. Every privileged mutation should call `logAdminAction()` afterward to write to `admin_action_log`. Follow this exact guard + log pattern for any new admin-only function.

**Customer/staff Edge Functions** gate through `supabase/functions/_shared/customer-guard.ts` instead, which exports two guards used by the ordering functions below:
- `requireCustomer()` — any authenticated user (not role-restricted; dine-in ordering isn't limited to the `customer` role, since staff can also place manual orders through the same function).
- `requireRestaurantStaff()` — requires `restaurant_owner`/`restaurant_staff` and returns the caller's own `restaurant_id` from their profile (never trust a `restaurant_id` from the request body — compare against this value).

Both return a service-role client after validating the JWT, same pattern as `admin-guard.ts`.

## Ordering flow (current model)

The ordering domain was reworked away from an earlier QR-code-per-table / `table_sessions` comanda model (no longer in `PDV.md`, which now documents the current model below) to this one:

- **Entry point is per-restaurant, not per-table**: the storefront route is `/loja/:restaurantId` (`src/pages/Mesa.tsx` → `TableProvider` in `src/lib/TableContext.tsx`, which now just resolves the restaurant + its `restaurant_branding`, no `qr_token`/table lookup). `src/lib/OrderChannelContext.tsx`'s `OrderChannelGate` asks once per browser session (`sessionStorage`, not `localStorage` — a refresh mid-order doesn't ask again, but a fresh visit later does) which of the three channels (`dine_in`/`pickup`/`delivery`) the customer wants; there is no `tables.qr_token` in the live flow anymore, and the table number (dine-in) is free text typed at checkout, not scanned. Logged-in customers don't retype their own name — `MesaCardapio.tsx` prefills `customerName` from `profile.full_name` (still editable, e.g. ordering for someone else at the table).
- **Every confirmed order is its own ticket.** There is no more session/comanda grouping multiple orders under one open tab — `restaurante/src/lib/tableSessions.ts` and the old `/mesas` page have been removed in favor of a unified `restaurante/src/pages/Pedidos.tsx` order board. Don't reintroduce `table_sessions`-based grouping without checking whether the table still exists/is used.
- **Cart is 100% client-side** (`src/lib/CartContext.tsx`, `localStorage` keyed by `restaurantId`) until the customer hits "Confirmar pedido". **A real (non-anonymous) account is required to check out** — `src/components/CustomerAuthModal.tsx` offers email/password signup+login and "Continuar com Google" (`supabase.auth.signInWithOAuth({ provider: "google" })`); the Google provider is enabled in the Supabase dashboard (Authentication → Sign In / Providers) with credentials from a dedicated Google Cloud OAuth client ("SIGMA PDV" — Authorized JavaScript origins/redirect URI need updating there if the storefront's domains change; the OAuth consent screen must also be in "Em produção" publishing status, not "Testando", or Google shows the raw Supabase domain instead of the branded app name on the account-chooser/consent screens — a separate step from "brand verification", which additionally requires proving domain ownership and is not yet done). The modal defaults to **login** (`mode: "login"`, "Já tenho conta" tab first/active), not signup — a first-time visitor tapping the account icon is more likely returning than brand new, and the old signup-first default confused people who already had an account. `src/pages/MesaCardapio.tsx`'s `goToLoginOrSubmit()` checks `useSession()`'s `isRealCustomer` (`session.user.is_anonymous === false`) and opens `CustomerAuthModal` if there's no real session yet; `signInWithOAuth` does a full-page redirect, but the cart survives it because `CartContext` already persists to `localStorage`. **Login is required to even open the cart, not just to submit** — `MesaCardapio.tsx`'s `handleCartClick()` (wired to both `Header`'s cart button and `OrderBar`) opens `CustomerAuthModal` with `authIntent: "cart"` instead of the drawer when `!isRealCustomer`; this is deliberate lead-capture (letting a guest build a whole order and only asking for login at the very end means losing the lead entirely if they abandon before that final prompt) and not just a submit-time gate. `handle_new_user` (see `supabase/migrations/0050_customer_profile_backfill.sql` — this backfills a schema change that had been applied directly to the remote DB without ever landing a migration file, `profiles.email`/`profiles.address` plus this trigger version) reads `full_name`/`phone`/`address` from `raw_user_meta_data` into `profiles` on signup; Google's OAuth metadata only ever supplies `full_name`+`email`, so `phone`/`address` stay null for Google signups until the customer fills them in via the profile screen. `src/lib/useSession.ts` (root app only — trimmed version of the `admin`/`restaurante` pattern, no `role`/`restaurant_id`) is the single source of truth for session/profile state.
- **Phone is a hard requirement to place an order, not just a signup-form field.** Manual signup already required it in the form, but a Google signup (which never supplies phone) or an old account that skipped it could previously check out with `customer_phone` silently omitted. `MesaCardapio.tsx`'s `goToLoginOrSubmit()` now blocks on `!profile?.phone` (real login+order flow) the same way a fresh authentication does (see below) — in both cases it opens `AccountOverlay`'s "Meu perfil" section with a banner and sets `pendingCheckoutAfterProfile`, which `handlePhoneSaved()` (passed as `AccountOverlay`'s `onPhoneSaved`, fired by the phone save button once the field is non-empty) uses to resume `submitOrder()` automatically — don't reintroduce the old `...(profile?.phone ? {...} : {})`-only best-effort behavior in `submitOrder()`'s body without this earlier gate, or the requirement becomes decorative again.
- **Post-authentication routing never auto-opens the account screen after a plain login, in any case — including entering via the account icon itself** (explicit product decision, not an oversight: it read as a jarring, unexplained popup). It only auto-opens when there's a real reason: checkout blocked on a missing phone (any mode), or a fresh **signup** that's still missing phone (Google signup, since manual signup already collected it in the form) — "welcome, let's finish your profile" reads as sensible there in a way an unprompted popup after login does not. `CustomerAuthModal`'s `onAuthenticated(mode: "login" | "signup")` now reports which happened (Google is always reported as `"login"` — it doesn't distinguish new vs. returning in this codebase — so a first-time Google signup only gets the friendly prompt if/when it hits the checkout-phone gate, not immediately on account-icon login); `MesaCardapio.tsx` stores `{ mode, intent }` in `pendingAuth` and resolves it in a `useEffect` gated on `useSession()`'s `loading` having settled (`profile` loads asynchronously *after* `session` changes — resolving synchronously inside `onAuthenticated` would race against a still-stale `profile`).
- **Customers manage their account through one full-screen overlay, `src/components/AccountOverlay.tsx`** (`fixed inset-0`, no bottom-sheet/modal chrome) — this replaced two separate components (`CustomerProfileSheet.tsx` bottom sheet, `MyOrderSheet.tsx` side drawer), each with its own `Header.tsx` icon and no way to move between them without closing one and opening the other. Now both icons (`Header`'s account icon and its "Meu pedido" clipboard icon) open the *same* `AccountOverlay`, only differing in which `section` (`"profile" | "orders"`) they pass in — `section`/`onSectionChange` are fully controlled by `MesaCardapio.tsx` (not internal state), so clicking the *other* icon while the overlay is already open switches section in place instead of no-oping or requiring a close/reopen. Navigation between the two sections is responsive: a top tab bar (`sm:hidden`) on mobile, a persistent left sidebar with "Sair" pinned at its bottom (`hidden sm:flex`) on desktop — "Meu perfil" (name/phone edit, read-only e-mail, password change, saved-address CRUD; content is the same as the old `CustomerProfileSheet.tsx`, just redesigned for full-screen width instead of a cramped `max-w-sm`) and "Meu pedido" (the current trackable order's status stepper + channel details/items, same content as the old `MyOrderSheet.tsx`, now with a **"Histórico de pedidos" list below it** — past orders at this restaurant, via the new `src/lib/orderHistory.ts`'s `useOrderHistory(restaurantId, customerId)`, which mirrors `useMyOrder`'s query/mapping — both re-exported from `myOrder.ts` as `SELECT`/`OrderRow`/`toMyOrder` instead of duplicating them — but with no `isTrackable`/3h-staleness filter and a `limit(20)` instead of `limit(1)`, since history is meant to show everything, including orders the "current order" tracker already stopped showing). Reads the customer's order(s) **at this restaurant** directly via RLS (`orders_select`'s `customer_id = auth.uid()` clause — no Edge Function needed for a read), with a realtime `postgres_changes` subscription (both hooks) filtered by `customer_id` only (Realtime doesn't support combining two `eq` filters with AND) that just triggers a full reload, which re-applies the `restaurant_id` filter itself. The order tracker is separate from and persists longer than the one-time "Pedido enviado!" full-screen confirmation in `MesaCardapio.tsx` (shown once, right after `submitOrder()` succeeds). The step labels are channel-specific (`STEP_LABELS` in `AccountOverlay.tsx`: dine-in's "Pronto" vs. pickup's "Pronto pra retirar" vs. delivery's "Saiu pra entrega"), same 4 real statuses (`received`/`preparing`/`ready`/`completed`) underneath — `cancelled` short-circuits to its own banner instead of the stepper. Deliberately does **not** embed `delivery_drivers` in either query — that table's RLS (`delivery_drivers_all`) only grants staff/admin, so a customer-facing embed would just silently resolve to `null`; don't add it back without a customer-facing RLS policy on that table first. Saved delivery addresses live in `customer_addresses` (`supabase/migrations/0048_customer_delivery_checkout.sql` — global per customer, not scoped by `restaurant_id`, since the address text is reusable across restaurants while the neighborhood/fee is chosen fresh each order) with a customer-chosen `label` (e.g. "Casa"/"Trabalho"/free text) settable both inline at delivery checkout (`CartDrawer.tsx`, only when typing a brand-new address, optional) and from `AccountOverlay`'s "Meu perfil" address list (`src/lib/customerAddresses.ts`'s `saveAddress`/`updateAddress`/`deleteAddress`, also `addressIcon()` mapping Casa/Trabalho/other to a lucide icon, shared by both screens). Since the neighborhood/fee can't live on the (cross-restaurant) saved address itself, `MesaCardapio.tsx` remembers it a different way: whenever a saved address is (re)selected for a delivery order, it queries the customer's own most recent order for `(restaurant_id, delivery_address->>text)` and pre-fills `neighborhoodId` from that order's `neighborhood_id` if found — reselecting the same address at the same restaurant later skips the "Bairro" dropdown instead of asking again every time.
- **`CartDrawer.tsx` has a "Revisar pedido" step before the real "Confirmar pedido"** — modeled on the iFood reference flow: tapping the totals-and-button footer's primary action first flips a local `reviewing` state to a read-only order summary (items, table/address/payment, customer name, totals) with "Voltar" to go back and edit, and only *that* screen's button actually calls `onConfirm` (price-check → login-check → submit). `reviewing` resets on close (the component never unmounts between cart open/close, so without this a later reopen would jump straight to review). The footer totals also show "Economia de R$ X" when applicable — summed from `CartItem.originalPrice` (set in `CartContext.tsx`'s `addItem()` from `product.original_price`, only for the plain-price case — a half-and-half line's price comes from a different product entirely, so it's left `undefined` there and contributes no savings).
- **`CartDrawer.tsx`'s body is a single scrollable region (items + the whole delivery form), with only the totals+button as a short fixed footer** — don't split it back into "scrollable items" + "non-scrolling form-and-footer". That was the original layout and had a real bug: the delivery form (address picker + bairro + payment + troco) alone could exceed 680px, and with no `overflow` on its container it just got clipped by the viewport on shorter phones (iPhone SE-class), leaving "Confirmar pedido" permanently unreachable with no scrollbar to get to it. The fix put every long, variable-height thing inside the one `overflow-y-auto` region and kept the footer to just totals + one button, which is short enough to always fit.
- **Menu items can carry addons, combos, half-and-half, and removable ingredients** — `src/lib/useMenu.ts` loads `addon_groups`/`addons` (optionally `required` per category), `combo_items` (fixed combo components), `combo_choice_groups`/`combo_choice_options` ("choose your burger" style combos), and `product_ingredients` (removable ingredients, no price effect). Half-and-half pricing (`categories.allow_half_and_half`, `half_and_half_pricing`: `higher_price` | `average`) picks a second product from the same category as an alternate flavor. Tapping a product in a half-and-half-enabled category (that has at least one other product to pair with) doesn't open `ProductDetailSheet` directly — `MesaCardapio.tsx`'s `handleOpenDetail()` routes it through `src/components/HalfAndHalfChoiceDialog.tsx` first: "Inteira" (whole) goes straight to the normal sheet, "Meio a meio" shows a second step listing every other product in that same category (always excluding the tapped product itself — pairing a flavor with itself makes no sense) and, once picked, opens `ProductDetailSheet` with that flavor pre-selected via its `initialHalfFlavorId` prop (the sheet's own "Meio a meio" section stays visible and editable afterward, in case the customer wants to change flavor without restarting the popup).
- **The Edge Function `place-dine-in-order` (`supabase/functions/place-dine-in-order/index.ts`) is the only write path for placing an order.** It never trusts client-supplied prices or selections: it re-resolves product price, addon price, required-addon-group satisfaction, half-and-half price (recomputed server-side via the same formula as `src/lib/halfAndHalfPricing.ts`), combo choice validity, and removable-ingredient membership, all from the database, before inserting `orders`/`order_items`/`order_item_addons`/`order_item_combo_choices`/`order_item_removed_ingredients`. Reuse this validation pattern for any new mutation that touches order pricing.
- **Order channels**: `order_type` is `dine_in` (needs `table_label`), `pickup` (server generates a per-day sequential `pickup_code`), or `delivery` (needs a free-text `delivery_address`). The root storefront drives all three today, chosen once per session via `OrderChannelGate` (see above); staff can also create any of the three manually through `ManualOrderModal` in `restaurante/`. `payment_method`/`change_for` are asked (and required to confirm) for `dine_in` too, not just `delivery` — `CartDrawer.tsx` renders that section for both channels, and `MesaCardapio.tsx`'s `submitOrder()` must include `payment_method`/`change_for` in the request body for both (a real bug shipped briefly: the UI collected them for `dine_in` but the body only forwarded them `orderType === "delivery"`, so the answer was silently dropped — if `place-dine-in-order`'s body-construction and `orderType` gating are ever touched again, keep the delivery-only fields, `delivery_address`/`neighborhood_id`, and the shared payment fields in separate conditionals like this, not one combined block). `pickup` still doesn't ask payment method — out of scope of that change.
- **Manual/staff-entered orders**: when the caller of `place-dine-in-order` is staff/admin (not a `customer`), `customer_id` is left `null` by default instead of the staff member's id, so the customer history doesn't get contaminated (see `0032_order_customer_id_nullable.sql`). Staff can optionally link the manual order to an existing customer account instead — `ManualOrderModal.tsx`'s customer dropdown (`restaurante/src/lib/restaurantCustomers.ts`'s `useRestaurantCustomers()`) only ever shows customers who already have order history *at this restaurant*, because that's all the `profiles_select_restaurant_customers` RLS policy exposes to staff (`role = 'customer' AND EXISTS (orders where customer_id = profiles.id AND restaurant_id = current_restaurant_id())`) — a customer's first order anywhere, or their account from a different restaurant, is invisible to staff here by design (no cross-tenant customer search). The server re-validates `body.customer_id` is really a `role = 'customer'` profile before writing it (never trusts the dropdown selection alone), same pattern as every other client-supplied id in this function.
- **`waiter_id` is dine-in only, enforced in both places**: `place-dine-in-order` only resolves/stores `waiter_id` when `order_type === "dine_in"` (delivery/pickup orders ignore it even if the client sends one — never trust the UI to hide a field correctly). The `restaurante/` UI mirrors this: `WaiterAssignSelect` only renders for `dine_in` orders in the Pedidos card, `OrderDetailModal`, and the `Garcom` (waiter workspace) page's order list — that page's `openOrders` filter also excludes non-dine_in orders entirely, since assigning/claiming a table waiter never made sense for a delivery/pickup order. `ManualOrderModal.tsx`'s "Garçom" field is likewise dine_in-gated, and clears the sent `waiter_id` if staff picks a waiter while on "Mesa" then switches the channel toggle before submitting — a real bug that shipped briefly (the field hid but the stale state still got submitted).
- **Choosing the delivery driver happens at the "Pronto" status transition, not via an always-visible dropdown**: `Pedidos.tsx`'s `handleAdvance()` intercepts a delivery order's `preparing → ready` transition (only when the restaurant has at least one active driver — otherwise advances straight through, never blocking the flow) and opens `AssignDriverModal.tsx` instead of calling `advanceStatus` directly; confirming there calls `assignDeliveryDriver` then `advanceStatus(..., "ready")` in sequence. The persistent `DeliveryDriverAssignSelect` that used to sit in the order card header is gone — `OrderDetailModal.tsx` still has one, kept as a manual correction path (wrong driver picked, needs reassigning) separate from the "which motoboy is taking this" decision point.
- **Staff order management** lives in `restaurante/src/pages/Pedidos.tsx`, backed by `restaurante/src/lib/orders.ts`'s `useIncomingOrders()` hook: a realtime (`postgres_changes` on `orders`) Kanban across `received → preparing → ready → completed` (plus `cancelled`), grouped/filterable by channel. The new-order sound notification (`restaurante/src/lib/orderSound.ts`, distinct chime for delivery vs. dine-in/pickup) does **not** live in this hook or this page — see "Ticket printing" below for where it actually lives and why.
- **Editing an already-placed order** (add/remove item, notes, discount, service charge) goes through the Edge Function `supabase/functions/staff-edit-order/index.ts` (`requireRestaurantStaff` guard), which — like `place-dine-in-order` — always re-resolves the item price from the database and always recomputes `subtotal`/`total` from scratch rather than incrementally. Registering a payment is the one mutation that doesn't touch pricing, so it goes through a direct RLS-gated update instead of this function.
- Financials: `orders.total = subtotal - discount_amount + service_charge_amount` (`0031_order_financeiro.sql`); `orders.notes` is a staff-entered free-text note (`0030_order_notes.sql`), separate from `order_items.notes` (per-item note).
- **Marketing tab** (`restaurante/src/pages/Marketing.tsx`, `/marketing`) lets staff set a Meta Pixel ID (`restaurant_branding.meta_pixel_id` — `0051_marketing_pixel.sql`, in `restaurant_branding` rather than `restaurants` specifically because `restaurants` UPDATE RLS is admin-only, see `0049_restaurant_settings.sql`, while `restaurant_branding` already lets staff write their own row) and generate two kinds of storefront link via `restaurante/src/lib/previewLink.ts`'s `usePreviewLink()` (same subdomain-or-`/loja/:id` resolution already used for "Ver como o cliente vê"): a paid-traffic link (`?canal=delivery`) and a table-specific link (`?canal=dine_in&mesa=N`). `src/lib/OrderChannelContext.tsx`'s `readInitial()` reads `?canal=` and skips the "how do you want to receive it?" picker entirely when present (URL wins over whatever channel was already in `sessionStorage`); `src/pages/MesaCardapio.tsx` reads `?mesa=` once, as the initial value of `tableLabel`, to prefill (not lock) the table number field. `src/lib/metaPixel.ts`'s `initMetaPixel()` (official Meta base snippet, guarded per-pixel-ID so it never double-injects) fires from `TableContext.tsx` once the restaurant resolves — `PageView` on load. Two more events, both fired client-side (no Conversions API/server-side tracking at this stage — that was evaluated for a "count the sale only once the restaurant marks the order delivered" model, but abandoned: it needs a cross-browser identity handoff via stored `fbp`/`fbc` plus a per-restaurant Conversions API access token, real complexity for a case the product doesn't actually have — `orders.status` can't reach `cancelled` once it's `completed`, see the Kanban note above, so a confirmed order is never later invalidated): `trackInitiateCheckout()` fires from `CartDrawer.tsx` when the customer taps "Revisar pedido" (entering the read-only review step, not on every cart open), and `trackPurchase()` fires with the server-computed `data.total` from `MesaCardapio.tsx`'s `submitOrder()` on success — i.e. the moment the order is actually placed counts as the sale, matching `orders.status = 'received'` rather than waiting for later fulfillment.

## Ticket printing

Automatic ticket printing has now been attempted four times; the first three were removed entirely (repo and database) before this one:

1. **QZ Tray / ESC-POS** — its free tier uses self-signed certs whose trust prompt cannot be permanently dismissed ("Remember this decision" is deliberately disabled for untrusted certs); the fix is a paid certificate or a manual `override.crt` drop into QZ's install dir — too much setup friction for non-technical staff.
2. **`printer-app/`, a .NET 8 WinForms+WebView2 kiosk shell** wrapping the Pedidos page and printing silently via `CoreWebView2.PrintAsync`. Avoided QZ's trust problem, but was removed along with everything else.
3. **PrintBridge, a DB-backed print queue** (`print_stations`/`print_pairings`/`print_jobs`, an `orders` insert trigger enqueuing jobs, and a paired native agent polling an Edge Function for work). Removed by `0040_remove_printbridge.sql` before the native agent side was ever finished — see that migration's comments; as with the attempt before it, an orphan `'print_agent'` value is left inert in the `app_role` enum on purpose (dropping it would require recreating the type with `CASCADE`, which would drop every RLS policy in the project). `0034_remove_print_infra.sql` tore down the *second* dead end's DB side the same way (`print_jobs`/`print_agents`/`print_agent_pairings` — note the singular/plural table-name collision with PrintBridge's own `print_jobs`, a different table entirely, added later).

**The current (fourth) attempt is Impressora PDV-Sigma, source in `agente/`** — a single Go binary (`ImpressoraPDVSigma.exe`, shown in the Windows tray as "Impressora PDV-Sigma"), no external runtime, running on a computer in the restaurant and serving an HTTP API on `127.0.0.1:18080` only. The `restaurante/` app talks to it directly via `fetch()` from the browser — no cloud queue, no pairing, no database table for printing at all. See `agente/README.md` for the full design, build/install instructions, and the HTTP API.

- **Why local instead of a queue**: the previous three attempts all tried to route printing through infrastructure (a trust-prompted local service, a bundled browser shell, a polling agent against a DB queue) instead of just letting the browser talk to a local process directly. `127.0.0.1` is a secure context for `fetch()`, so no TLS/certificate story is needed — that alone kills the QZ Tray dead end. A local HTTP agent needs no queue to poll and no pairing handshake to keep in sync with the restaurant's `restaurant_id`, because the browser page (which already knows which restaurant it's logged into) talks to the agent directly.
- **The DSL lives in the frontend, not the agent**: `restaurante/src/lib/escposDoc.ts` builds a declarative command array (`{op: "text"|"columns"|"line"|"feed"|"cut", ...}`) from an `IncomingOrder` (see `restaurante/src/lib/orders.ts`); the agent's `internal/escpos/renderer.go` only knows how to turn that DSL into ESC/POS bytes (CP860 code page, partial cut, column widths for 58mm/80mm paper). This split means a formatting fix is a frontend deploy, not a re-distributed `.exe` — same reasoning the DB-DSL had in PrintBridge's `escpos-doc.ts`, just moved one hop over now that there's no server in the loop.
- **Origin allowlist, not TLS or pairing, is the security boundary**: the agent only answers requests whose `Origin` header is in a build-time allowlist (`agente/internal/httpapi/buildconfig.go`, extendable per-station via `extraOrigins` in `config.json`); anything else gets `403` and never learns the agent exists. **Incident**: `defaultAllowedOrigins` shipped with only the dev origins (`localhost:5175`/`127.0.0.1:5175`) for a while after `restaurante/` went live on `https://app.assessoriasigma.com.br` (see Vercel → `sigma-pdv-restaurante` → Domains for the current list) — every real client's browser got silently `403`'d, which looks exactly like "the printer software isn't running" from the restaurant's side even though the tray app is up. Fixed in `buildconfig.go` (both the custom domain and the `sigma-pdv-restaurante.vercel.app` fallback added to `defaultAllowedOrigins`, `Version` bumped to `1.1.0`) — whenever a new production domain is added (new custom domain, staging environment, etc.), add it here too and republish, don't rely on someone remembering to hand-edit `extraOrigins` on every installed station.
- **Scope is ESC/POS only, deliberately** — the agent is `CGO_ENABLED=0` Go, no MuPDF/cgo, so it cross-compiles cleanly and stays a ~6MB single file. `POST /print` with `formato: "pdf"` responds `501 Not Implemented`; there is no PDF/A4 rendering path.
- **Known constraint, not a bug**: Chrome 142+ requires a Local Network Access permission prompt (replacing the old Private Network Access model) the first time a public `https://` origin's page fetches a `127.0.0.1` address; it must be triggered by a user gesture. `localhost` dev origins are exempt. This is why `/impressora`'s "Imprimir página de teste" button exists as an explicit click rather than the page silently auto-detecting the agent on load — see `agente/README.md` for detail.
- **Tray icon, not a Windows Service, on purpose**: the agent shows a system tray icon (`agente/internal/trayapp/`) with an "Iniciar com o Windows" toggle (`agente/internal/autostart/`, an `HKCU\...\Run` registry entry) so it launches automatically at login. It is deliberately not a Windows Service — a Service runs in Session 0 before any login, with no desktop access at all, which is incompatible with showing a tray icon. Since a restaurant till stays logged into one Windows account all day, login-triggered start covers the real case without giving up the tray icon.
- **Auto-print + the new-order sound live in `RestaurantLayout.tsx`, not in `Pedidos.tsx`** (`restaurante/src/lib/autoPrint.ts`'s `useAutoPrintOnNewOrders`, mounted in `restaurante/src/components/RestaurantLayout.tsx` outside the `<Outlet/>`). This was a real bug, not a design choice made up front: it originally lived inside the Pedidos page component, so a new order only triggered a printout or a sound while staff had the Pedidos board open — closing it (e.g. to work in Cardápio or Dashboard) silently stopped printing. `RestaurantLayout` wraps every route and never unmounts on navigation, so the realtime `orders` INSERT listener there fires regardless of which screen is open. `useAutoPrintOnNewOrders` fetches the full order via `orders.ts`'s `fetchOrderById()` (a single-order query, since the layout doesn't have the whole board's order list loaded) rather than reusing `useIncomingOrders()`. Don't move this back into `Pedidos.tsx` — that's the exact regression this fixed. The manual reprint button (per order card) stays in `Pedidos.tsx`, since it's a deliberate action taken while already looking at that order.
- **The installer is downloadable from inside the app**: `/impressora` (`ConfiguracaoImpressao.tsx`) has a "Baixar ImpressoraPDVSigma.exe" button pointing at `/downloads/ImpressoraPDVSigma.exe`, served as a static file from `restaurante/public/downloads/` (Vite copies `public/` verbatim into the build — no Storage bucket, no CDN, no release pipeline at this stage). That means the compiled `.exe` (~7MB) is committed to git like any other static asset; publishing a new agent build means manually copying the freshly built binary into that path (see `agente/README.md`, "Publicar uma versão nova") before deploying `restaurante/`.
- **The agent self-updates, so a fix like the allowlist incident above only needs publishing once** — `agente/internal/autoupdate/` checks `restaurante/public/downloads/latest.json` (same trusted production domain) at startup and every 6h while running; if the manifest's version is numerically newer, it downloads the `.exe`, verifies the manifest's declared SHA-256, and swaps the binary in place (rename-current-to-`.old`, rename-new-into-place, spawn the new process). The synchronous startup check runs before the tray/HTTP server open at all, covering the common case (Windows login each morning); the periodic 6h check instead waits for the new process to answer `/health` before discarding the old one — if it doesn't respond within 15s (broken build), it rolls back automatically (old binary restored, broken one kept as `<exe>.new.broken` for inspection) rather than bricking the station. Trust model is HTTPS + checksum-from-the-same-domain, same level the manual download already had — **not code signing**; a compromised deploy pipeline could push a bad update to every installed station, an accepted tradeoff at this stage, not an oversight. Publishing a new build now requires bumping **two** sources of truth together — `httpapi.Version` in `buildconfig.go` and `latest.json`'s `version`/`sha256` — see `agente/README.md`'s "Auto-update" and "Publicar uma versão nova" sections; forgetting `latest.json` doesn't break the manual download button, it just means installed stations never notice the new version exists.

Don't reintroduce a print queue table, a pairing/token handshake, or a bundled third-party executable without re-reading this section and `agente/README.md` first.

## Cobrança (Cakto)

Um único plano (R$350/mês, assinatura recorrente) via [Cakto](https://cakto.com.br) — o restaurante só usa o painel (`restaurante/`) com `restaurants.status = 'active'`; sem isso, `ProtectedRoute.tsx` redireciona toda rota (exceto `/cobranca` e `/bem-vindo`, senão o dono nunca conseguiria chegar na tela de pagamento) pra `/cobranca` (`Cobranca.tsx`). **O storefront público (root app) não é bloqueado por isso** — a cobrança trava só o back-office do restaurante, não o cardápio que os clientes finais já usam.

- **Produto/oferta são únicos e compartilhados, não um por restaurante**: criados uma vez no painel da Cakto (produto "cadapio sig", oferta padrão id `3edmmmm`, tipo `subscription`, R$350, recorrência de 30 dias, sem limite de ciclos — `intervalType: lifetime` só controla duração de acesso por ciclo, não a cobrança em si, que segue por `recurrence_period`/`quantity_recurrences`). `cakto-create-checkout` (`requireRestaurantStaff`) só monta a URL `https://pay.cakto.com.br/{offer_id}` pré-preenchida com nome/e-mail/telefone do dono logado — não chama a API da Cakto em tempo de execução (as credenciais client_id/client_secret só foram usadas uma vez, num setup manual/local, pra criar a oferta e cadastrar o webhook; não estão guardadas em lugar nenhum do runtime).
- **Correlação de pagamento por restaurante via `sck`, não por e-mail**: como várias contas de restaurante pagam contra a MESMA oferta, `cakto-create-checkout` bota `sck=<restaurant_id>` na query string do checkout — a Cakto ecoa esse parâmetro de volta em `data.sck` no payload do webhook (é o mesmo campo de tracking que ela usa pra UTM/origem de venda, documentado como "usado internamente pra rastrear algo específico"). E-mail do cliente (`data.customer.email` batido contra `profiles.email`) é só fallback pra checkout aberto sem passar por `cakto-create-checkout` (link colado à mão).
- **`cakto-webhook` é pública (`verify_jwt: false`)** — a Cakto não manda JWT do Supabase nem assina o payload com HMAC/header; a autenticidade vem de um campo `secret` dentro do próprio corpo do POST, comparado em tempo constante contra `CAKTO_WEBHOOK_SECRET` (gerado pela Cakto na hora de cadastrar o webhook, **precisa ser configurado manualmente como secret da Edge Function** — não há tool MCP do Supabase pra isso e o ambiente que criou essa integração não tinha `SUPABASE_ACCESS_TOKEN` pra usar a CLI; ver `supabase secrets set CAKTO_WEBHOOK_SECRET=...` ou o dashboard, Project Settings → Edge Functions → Secrets). Sem esse secret configurado, a function recusa tudo com 503 em vez de aceitar sem checar (visto na prática: `event_test` da Cakto contra o webhook recém-cadastrado bateu certinho nesse 503 antes do secret ser configurado).
- **Eventos da Cakto viram três categorias** (ver `ACTIVE_EVENTS`/`SUSPEND_EVENTS`/`WARNING_EVENTS` em `cakto-webhook/index.ts`): `purchase_approved`/`subscription_created`/`subscription_renewed`/`subscription_resumed` ativam (`restaurant_billing.status = 'active'` + `restaurants.status = 'active'`); `subscription_canceled`/`chargeback`/`refund` suspendem (`restaurants.status = 'suspended'` — nunca `'cancelled'`, esse valor fica reservado pra ação manual do admin); `purchase_refused`/`subscription_renewal_refused`/`subscription_paused` só registram `past_due` em `restaurant_billing` sem mexer em `restaurants.status`, já que a Cakto ainda vai tentar cobrar de novo sozinha (`max_retries`/`retry_interval` da oferta) — suspender numa falha isolada de cobrança seria prematuro.
- **`restaurant_billing`** (`0060_restaurant_billing_cakto.sql`) é só leitura pro staff/admin via RLS (`current_restaurant_id()`/`current_app_role() = 'admin'`, mesmo padrão do resto do projeto) — toda escrita é service-role de dentro das duas Edge Functions, nunca direto do cliente. `restaurante/src/lib/billing.ts`'s `useRestaurantBilling()` tem realtime (`postgres_changes` filtrado por `restaurant_id`) pra `Cobranca.tsx` sair da tela de bloqueio sozinha assim que o webhook confirmar o pagamento, sem precisar de F5.

## Frontend conventions

- React 19 + TypeScript + Vite + Tailwind v4 (via `@tailwindcss/vite`, no separate config file) + `lucide-react` icons. `restaurante/` additionally uses `@dnd-kit/*` for drag-and-drop menu ordering.
- `admin/` and `restaurante/` use `react-router-dom` v7 with a shared `ProtectedRoute` component gating on `useSession()` (session + profile fetch from Supabase); the root storefront app routes with `react-router-dom` too (`src/App.tsx`: `/` and `/loja/:restaurantId`).
- Supabase client setup lives at `<app>/src/lib/supabase.ts`; Edge Function error messages are normalized through `<app>/src/lib/functionError.ts`'s `describeFunctionError()` — use it instead of surfacing raw `FunctionsHttpError` bodies.
- Environment variables: `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` in each app's `.env.local` (see `.env.local.example`).
- Menu/product images go to the public-read `menu-images` Storage bucket under `{restaurant_id}/{categories|products}/{uuid}.{ext}`; the write policy pins each tenant to its own folder via `storage.foldername(name)[1] = current_restaurant_id()`, so keep that path shape when uploading.
